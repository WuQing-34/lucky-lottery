# 幸运大转盘 —— 抽奖系统

一个**零依赖**的抽奖网页系统，用 Python 标准库写的（`http.server` + `sqlite3`），
不需要 `pip install` 任何东西，装了 Python 就能跑。**手机浏览器直接可用**。

- **用户端**：`http://<地址>:8000/`
- **管理端**：`http://<地址>:8000/admin` （默认密码 `admin888`）

> **当前版本 v3.0.0** 的核心变化：**每个奖品一个扇区，各自独立概率与库存，抽中即定**
> （不再有「中奖后再选礼品」这一步）；支持**测试ID**（抽奖不消耗正式库存）；某个奖品
> 发完后**不下架、不标注已抢完，只是永远抽不到**；并发承载已按 600 峰值做过专项优化。

## 一、怎么跑起来

### 本机运行

1. 确认已安装 Python 3.8 以上（命令行执行 `python --version` 能显示版本号即可）。
   没装的话去 https://www.python.org/downloads/ 下载，**安装时务必勾选 "Add Python to PATH"**。
2. 双击 `start.bat`。
3. 窗口里会打印两个地址，浏览器打开即可：

   ```
   用户端：http://127.0.0.1:8000/
   管理端：http://127.0.0.1:8000/admin
   局域网：http://192.168.x.x:8000/   （同事手机/电脑可直接访问）
   ```

关掉窗口或按 `Ctrl+C` 即停止服务。**抽奖数据存在 `data/lottery.db`，重启不丢。**

### 让外网/同事能访问

服务默认监听 `0.0.0.0:8000`，同一局域网内的设备用启动时打印的那个"局域网"地址就能访问。
**手机连同一个 Wi-Fi，直接输那个局域网地址即可参与抽奖**，不需要额外配置。

如果要放到公网服务器上：

```bash
python3 app.py --port 80          # 换端口
PORT=8080 python3 app.py          # 或者用环境变量
nohup python3 app.py --port 8000 > lottery.log 2>&1 &    # 后台常驻
```

上线前记得改管理密码（管理端 → 系统设置 → 修改管理密码）。

### 用户端

1. 输入用户ID → 校验资格
2. 点击转盘中心按钮抽奖（转盘上**每个奖品一个扇区**，会转 5～7 圈后停在结果扇区）
3. **中奖后**直接填写**收货信息**（不用再选东西，抽中什么就是什么）：
   省 / 市 / 区县三级**下拉框** + 详细地址、收货人姓名、联系电话（文本框）
4. 提交结果实时进入管理端的抽奖记录，并出现在发货表导出里（E 列 = 抽中奖品的物料编号）

另外支持**专属链接**：`http://<地址>:8000/?uid=10001`，用户打开即自动登录，不用手输ID。
发到群里最省事。

### 「多个奖品 · 各自独立」怎么运作

- 转盘上**每个奖品一个扇区**，扇区大小 = 该奖品在「奖品与概率」里填的概率。
  概率之和不足 100% 的部分自动成为「谢谢参与」；超过 100% 时按比例压回 100%。
- **每个奖品各有自己的库存**：每中一次扣 1，互不影响（`-1` = 不限量）。
- 抽中即定，中奖记录里同时存下该奖品的**物料编号快照**；发货表 E 列就是用这个编号。
  编号后来才补填也没关系 —— 导表时会回查奖品表补齐。
- **某个奖品发完后**：它的扇区**仍留在转盘上**（不消失）、**不显示「已抢完」**，
  但概率被静默归零 —— 无论怎么转都抽不到（需求：不标注已抢完）。
- **测试ID 不受库存限制**：正式库存抽光了，测试号照样能继续中奖，方便联调。

## 三、发货表导出（重点）

下游系统要的是一张**固定表头、11 列**的 CSV，管理端「导出发货表」直接产出，
不需要任何手工加工。表头和取值规则如下：

| 列 | 表头 | 取值规则 |
|---|---|---|
| A | `学生ID*` | 中奖用户ID |
| B | `部门编号*` | 固定 `1000003263`（可在系统设置里改） |
| C | `标题` | 固定 `双节课消活动礼品`（可在系统设置里改） |
| D | `业务订单编号` | 固定 `双节课消活动礼品`（可在系统设置里改） |
| E | `物料信息*` | **学员抽中的奖品的物料编号 + `*1`**，例如编号 `123` → `123*1`。数量固定 `*1` |
| F | `省` | 用户下拉框选择 |
| G | `市` | 用户下拉框选择 |
| H | `区/县` | 用户下拉框选择 |
| I | `详细地址` | 用户文本输入 |
| J | `收货人电话` | 用户文本输入 |
| K | `收货人姓名` | 用户文本输入 |

导出规则细节：

- **两种范围**：`已填收货信息`（只导已提交收货信息的，默认）和 `全部中奖记录`（含未填的）。
  两个按钮就在管理端「导出发货表」卡片里。
- **物料编号是"抽奖那一刻"的快照**。记录里存了中奖时的编号，所以事后改奖品编号、
  甚至删掉奖品，历史记录的编号都不会变。
  取数顺序：`奖品当前编号 → 记录里的编号快照 → 空`。
- **没配编号的奖品**：E 列输出空值（不会写出 `*1` 这种残缺值），同时响应头带
  `X-No-Code-Count`，页面会提示"有 N 条记录缺物料编号"，让你先去补编号。
- **文件编码**：UTF-8 + BOM，Excel 双击打开不乱码；文件名形如
  `shipping_20261008_183000.csv`。
- 编号里如果混入了 `*`（复制粘贴常见），保存时会自动去掉，避免拼出 `123**1`。

## 四、省 / 市 / 区县下拉框

用户侧不再让自己手打地址，改成三级联动下拉框：

- 数据源是随程序附带的 `regions.json`（本地文件，**不联网**）：
  **34 个省级 / 366 个市级 / 3439 个区县级**，覆盖中国大陆 + 港澳台。
- 交互：选省 → 市级下拉激活并填充；选市 → 区县下拉激活并填充。
  未选上一步时下层下拉是**灰色不可点**状态，而不是空的（避免用户瞎点）。
- **直辖市**（北京/上海/天津/重庆）：市一级自动选中同名项，用户只需再选区县，少点一次。
- 港澳台（香港/澳门特别行政区、台湾省）在下拉框里同样可选。
- 接口 `/api/regions` 带 `ETag` + `Cache-Control: public, max-age=86400`，
  浏览器第一次拉完就缓存，再次进入不重复下载；数据变更后 ETag 变化自动失效。
- 三级（省/市/区县）**必须都选**才能提交收货信息，后端也会二次校验，不只靠前端。

## 五、关于「同一个ID只能抽一次」

这是需求里最硬的一条，做了三层保证：

1. **数据库唯一约束**：`records` 表的 `uid` 字段建了 `UNIQUE` 索引。这是最终防线，
   就算并发请求同时打进来，数据库层也只会接受一条。
2. **写事务 + 进程锁**：抽奖走 `BEGIN IMMEDIATE` 事务，外面还加了一道 `threading.Lock`，
   先检查再写入这段逻辑不可能被穿插。
3. **不提供删除记录的接口**：管理端没有任何"删除抽奖记录"的入口，
   就是为了让"一次即永久"不可撤回。用户刷新页面、清缓存、换浏览器、换设备都没用——
   服务端记录的是用户ID，不是浏览器状态。

**已实测验证**：
- 同一ID连续抽 2 次 → 第 2 次直接返回"已抽过"，奖品不变
- 同一ID并发 10 个请求同时抽 → 只有 1 次成功，其余 9 次都被拦
- 刷新页面重新登录 → 仍然显示已抽过的结果，不重新进入转盘

> 真要给某人"补一次机会"，只能人工改数据库（删掉那条记录），
> 这是刻意留的唯一后门，别把它做成界面按钮。

## 六、概率是怎么算的

概率单位是**百分比**，可以填小数。**不需要凑成 100**：

- 所有奖品概率之和 < 100 → 剩下的部分自动成为「谢谢参与」扇区
- 所有奖品概率之和 > 100 → 按比例归一化，不再有未中奖扇区
- 所有奖品概率都是 0 → 整盘只有「谢谢参与」

转盘上每个扇区的**角度和真实中奖概率严格对应**（扇区角度 = 概率 × 3.6°），
不存在"看着大其实抽不到"的视觉欺骗。

**库存**：填 `-1` 表示不限量；填具体数字时，该奖品中出数量达到上限后**自动从转盘上移除**，
剩余概率并入「谢谢参与」。

**奖品名建议写短一点（4-5 个字最好）**。转盘上每个扇区要沿半径方向写字，名字太长会画不下——
程序会自动省略前缀或截断（完整名字始终显示在转盘下方的图例里）。概率极低的奖品（比如 1%）
扇区太窄，本来就不可能塞下文字，这时转盘上只留色块，靠下方图例对应。

## 七、文件结构

```
lottery/
├── app.py                后端（全部逻辑，单文件）
├── regions.json          全国省/市/区县数据（34省 / 366市 / 3439区县）
├── start.bat             Windows 一键启动
├── README.md             本文件
├── templates/
│   ├── user.html         用户端页面（含三级联动下拉框 + 手机端适配）
│   └── admin.html        管理端页面（含物料编号列 / 发货表导出 / 表格卡片化）
├── screenshots/          界面截图（16 张）
└── data/                 首次运行自动生成
    ├── lottery.db        SQLite 数据库 ← 备份就复制这个文件
    └── config.json       管理密码哈希、会话密钥
```

**备份**：直接复制 `data/` 整个目录，或者只复制 `lottery.db`。
**迁移**：把整个 `lottery/` 目录拷到另一台机器，双击 `start.bat` 即可
（`regions.json` 必须一起拷，否则下拉框会报"行政区划数据文件缺失"）。

**老库升级**：如果拿的是上一版的 `lottery.db`，直接启动即可——
程序会自动 `ALTER TABLE` 补上 `prizes.code`、`records.province/city/district/prize_code`
这些新字段，并写入部门编号/订单字段的默认值。**重复启动安全（幂等），不会重复改表。**

## 九、开发时的验证记录

下面这些是交付前真实跑过的测试，不是"应该没问题"：

| 验证项 | 方法 | 结果 |
|---|---|---|
| 概率是否真按配置走 | 独立脚本采样 200,000 次 | 实测偏差 < 0.23%（配置 1%/5%/12%/22%/60%） |
| 转盘落点是否对准扇区 | Node 抽取页面真实函数，校验 10,000 次落点 | 0 次越界，每次旋转 5-7 圈 |
| 同一ID并发抽奖 | 10 个请求同时打同一ID | 只有 1 次成功，其余 9 次被拦 |
| 刷新/重新登录能否重抽 | 重复调用登录与抽奖接口 | 一律返回"已抽过"，不回到转盘 |
| 库存耗尽 | 单奖品概率 100%、库存 3，连抽 12 次 | 正好中 3 次，之后全部未中奖，奖品自动移出转盘 |
| 概率和超 100 | 手动配成 334% | 自动按比例归一化到 100% |
| 全部概率为 0 | 手动改 | 整盘只有「谢谢参与」 |
| 收货信息校验 | 错误手机号、未中奖ID提交、重复提交、**省市区县缺项** | 都被拦截或幂等返回 |
| 改密码 | 改后立即用新旧密码登录 | 旧密码失效，新密码生效 |
| 冷启动 | 删掉 data/ 后重新启动 | 自动建库、建表、写入默认奖品与密码 |
| **发货表表头与列数** | 逐字符比对导出的 CSV 首行 | 11 列、表头与需求文档**完全一致** |
| **B/C/D 固定值** | 检查每行数据 | 全部为 `1000003263` / `双节课消活动礼品` / `双节课消活动礼品` |
| **E 列 `编号*1`** | 给奖品配 `123`，抽中后导出 | 输出 `123*1`；未配编号的奖品输出空值 |
| **未中奖不入表** | 库中混入「谢谢参与」记录后导出 | 未中奖记录被正确排除 |
| **导出两种范围** | `scope=filled` 与 `scope=win` 各导一次 | 前者只含已填地址的，后者含全部中奖记录 |
| **缺编号告警** | 故意留一个奖品不配编号 | 响应头 `X-No-Code-Count` 数量正确，页面提示到位 |

### 并发承载（600 峰值）专项

需求方给的极端峰值是 600 人同时抽。做了压力测试，并顺带查出并修掉了两个真实热点：

| 项目 | 优化前 | 优化后 |
|---|---|---|
| 单次「登录+抽奖」往返 | 64.8 ms | **13.8 ms** |
| 600 并发（barrier 同刻发起） | 22.0 s，51 个失败 | **1.5～2.0 s，0 个失败** |
| 吞吐 | 55 req/s | **400～600 req/s** |
| 单次 DB 查询 | ~30 ms | **0.012 ms** |

修掉的两个热点（数值是本机实测，Linux 上同量级）：

1. **每次连接都执行 `PRAGMA journal_mode=WAL`** → 每条连接多花 ~12 ms。
   WAL 是数据库文件的**持久属性**，设一次就永久生效，现在只在启动时设一次。
2. **每条连接上第一条真实读语句要额外付 ~26 ms**（打开库文件、加载页缓存；
   这段在 GIL 之外，所以 600 个并发会各扛一次，表现为"并发一上来每个请求就 30 ms+ 才响应"）
   → 改成**复用已预热的连接池**（启动预热 24 条，`DB_POOL_MAX=64`），
   借用/归还由锁保护、池空即新建，不会阻塞请求。

另外为应对突发连接做了**白保障**，不需要改动即可生效：

- `PooledHTTPServer`：固定 256 工作线程 + 连接排队（`MAX_QUEUED=4096`），
  超出部分排队等而不是被内核重置 —— 用户看到"稍慢"而不是"抽不了"。
- `LISTEN_BACKLOG=1024`（默认只有 5），突发连接有地方排队。
- 库存安全靠 `BEGIN IMMEDIATE` + 全局写锁串行化，**与并发数无关**：
  600 并发打 300 库存，实测**恰好 300 中奖**，不多不少。

> 测试环境注意：本机沙箱里有 `HTTP_PROXY`，它对单机连接数上限约 260，不绕开就会
> 测出假的 `503 proxy overloaded`。压测脚本已显式 `ProxyHandler({})` 绕开。
> 实际 Linux/Docker 部署无此限制。另外**客户端每次新建 `opener` 要 83 ms**、
> 复用只要 5.9 ms —— 压测脚本必须复用 opener，否则测的是客户端不是服务端。

#### 线上真机实测（2 核 2G · Docker · 公网 80 端口）

已在实际腾讯云轻量服务器 `62.234.140.218` 上跑过 600 并发（barrier 同刻发起）：

| 场景 | 结果 |
|---|---|
| 600 并发 `POST /api/user/login`（公网往返） | **600/600 全部 200，0 连接失败，1.63 s，368 req/s** |
| 600 并发抽奖、库存 300（本机同构环境） | 中奖**恰好 300**，0 重复 uid，0 HTTP 失败 |
| 看板 300 次并发读 | 0.47 s，635 req/s，全部 200 |

**结论：600 峰值可承载且有余量。** 冗余来源见上面的线程池 + backlog + 连接池三项；
即便峰值再翻一倍到 1200，也只是"稍慢"而不是"抽不了"。真正的瓶颈会是 2 核 CPU
（Docker 里 Python 单进程 GIL 受限），届时的第一手段是把 `WORKER_THREADS` 调到
512、`LISTEN_BACKLOG` 保持 1024，仍然不够再考虑多实例 + Nginx 反代。

## 十、安全提醒

- 默认密码是 `admin888`，**上线前必须改**。
- 本项目是内网/活动用的轻量工具，没有做 HTTPS、验证码、防刷限流。
  要放公网的话，建议挂在 Nginx 后面加上 HTTPS 和访问限制。

- 发货表里有**收货人姓名、电话、详细地址**（个人敏感信息），导出后的文件请按公司数据
  合规要求存放和流转，别随手丢在公共盘或聊天群里。
